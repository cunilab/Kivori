# Wokwi pre-hardware simulation gate

Runs the **real** Kivori ESP32-C3 firmware in the [Wokwi](https://wokwi.com) simulator so the embedded
runtime, protocol loop, lifecycle state machine, and renderer integration can be exercised **before**
anyone flashes a board.

> **Simulation does not replace physical validation.** A green Wokwi run says the firmware's logic
> executes correctly on a simulated RISC-V core. It says nothing about whether the product works on real
> hardware. The physical checks in [`docs/validation.md`](../../docs/validation.md)
> remain mandatory and unchecked until someone runs them on a device.

## Four modes, four artifacts

| Mode | Feature | Artifact | Diagram | What drives the device |
|---|---|---|---|---|
| **Internal on-target self-test** | `wokwi` | `target/wokwi/kivori-selftest.elf` | `diagram.json` (UART0 monitor) | an in-firmware harness — this is an *integration self-test*, **not** an external serial-transport test |
| **External serial test** | `wokwi-serial` | `target/wokwi/kivori-serial.elf` | `diagram-usb-serial.json` (`serialInterface: USB_SERIAL_JTAG`) | Wokwi `write-serial` injects **real wire frames** from outside; the firmware's real USB Serial/JTAG rx/tx loop, decoder, sequence policy, and `Dispatcher` handle them |
| **Production runtime** | `wokwi-runtime` | `target/wokwi/kivori-runtime.elf` | `diagram-runtime.json` (USB Serial/JTAG + generic display + logic analyser) | **the real `runtime::run` loop** — the same function the physical firmware calls, with a simulation-only board profile. The strongest evidence in the gate: it is the shipping loop, not a harness |
| **Generic SPI display probe** | `wokwi-spi` | `target/wokwi/kivori-spi.elf` | `diagram-spi.json` (`wokwi-ili9341` as a *generic* SPI sink) | the real T072 `mipidsi` `DisplaySink` over the real esp-hal SPI peripheral; counted at the `embedded-hal` boundary and captured as a VCD |

The external mode is the stronger evidence: bytes genuinely enter the device from outside. Injected bytes
are generated by [`tools/wokwi-vectors`](../../tools/wokwi-vectors) from the real `kivori-protocol` codec,
so no wire-format constant is duplicated for tests. Regenerate with:

```bash
cargo run -p kivori-wokwi-vectors     # writes sim/wokwi/generated/ (CI fails on a stale diff)
```

Neither mode creates an operating-system serial port: **the Tauri desktop cannot open a Wokwi device.**

## How it works

Wokwi automation supports both directions: `wait-serial` asserts on serial **output**, and `write-serial`
accepts a **byte array**, so real binary frames can be injected as serial **input**. The supported step
vocabulary was verified against the CLI's own validator (v0.26.1): `wait-serial`, `write-serial`, `delay`,
`set-control`, `expect-pin` are accepted; `wait-pin`, `screenshot`, `wait-text` are not.

* The **internal** self-test ([`selftest.rs`](../../firmware/esp32-c3/src/selftest.rs)) drives the core
  from inside via [`LoopbackTransport`](../../firmware/esp32-c3/src/sim_probe.rs), printing one
  `KIVORI-SIM …` line per check. Useful, but it is an on-target *integration* self-test — it does not
  exercise the serial peripheral.
* The **external** mode ([`external.rs`](../../firmware/esp32-c3/src/external.rs)) is the real thing:
  injected bytes arrive through the USB Serial/JTAG peripheral via
  [`transport.rs`](../../firmware/esp32-c3/src/transport.rs) (the same adapter the hardware run loop will
  use), pass through the real decoder + sequence policy + `Dispatcher`, and the device's real response
  frames go back out over the same peripheral. Redacted `KIVORI-EXT …` markers report the semantics.

Nothing under test is simulation-specific:

| Layer | In simulation | On hardware |
|---|---|---|
| Protocol codec, dispatcher, lifecycle FSM | identical (`kivori-protocol`, `proto.rs`, `state.rs`) | identical |
| Renderer, scene model, compiled asset bundle, RGB565 tiles | identical (`kivori-renderer`, same blob bytes) | identical |
| Clock | `EspClock` (esp-hal system timer) | same `EspClock` |
| Transport | **real `UsbJtagTransport`** (external mode); `LoopbackTransport` probe (internal mode) | same `UsbJtagTransport` |
| Display | `TileProbe` (internal mode); **real `MipidsiSink`** over real SPI (`wokwi-spi` mode) against a *generic* display part | same `MipidsiSink`, with the **confirmed** panel model and its real offsets |

There is **no separate simulation renderer** — that would violate Constitution II.

## Usage

```bash
bash scripts/build-wokwi-firmware.sh              # builds all FOUR ELFs into target/wokwi/
export WOKWI_CLI_TOKEN=...                        # CI token; never committed, never in argv
bash scripts/test-wokwi.sh                        # runs all eight scenarios
bash scripts/test-wokwi.sh boot spi-display-probe  # or a subset, matched by name
```

`wokwi-cli` must be installed (`curl -L https://wokwi.com/ci/install.sh | sh`, then
`export PATH="$HOME/.wokwi/bin:$PATH"`). Both the CLI and the token are required; the script exits with
status 2 and an explanation rather than reporting a false pass.

### The token must be a CI token

`WOKWI_CLI_TOKEN` must be a **CI token** from <https://wokwi.com/dashboard/ci> (short, `wok_…` shaped).
An interactive user/session credential — for example the long JWT that `wokwi-cli` writes to
`~/.wokwi/user.tok` after a browser login — is **not** a CI token: the CLI connects to the Simulation API
and the API answers `Unauthorized`. If you see:

```
Connected to Wokwi Simulation API 1.0.0-…
API Error: Unauthorized
```

the transport and the project are fine; the credential is the wrong type, revoked, expired, or from a
different account. Mint a CI token and re-export it. Never commit a token; never put it in workflow YAML
(CI reads `secrets.WOKWI_CLI_TOKEN`).

## Scenarios

Internal self-test (hand-written, no injection):

| Scenario | Asserts |
|---|---|
| [`boot.yaml`](scenarios/boot.yaml) | firmware boot, monotonic/advancing clock, `booting` → `offline` |
| [`protocol.yaml`](scenarios/protocol.yaml) | dispatch loop, `Hello`/`HelloAck` + nonce, identity, capability advertisement, major-version rejection, `Ping`/`Pong`, malformed-frame recovery |
| [`state-cycle.yaml`](scenarios/state-cycle.yaml) | `SetState`/`StateReport`, `booting`/`offline` never sendable, compiled-asset parse, 6×240×40 RGB565 tiles, change-driven refresh, safe diagnostics |

External serial injection (generated — contain real wire bytes):

| Scenario | Asserts |
|---|---|
| [`generated/serial-smoke.yaml`](generated/serial-smoke.yaml) | readiness marker, one real `Ping` frame received over USB Serial/JTAG, `Pong` response path |
| [`generated/protocol-serial.yaml`](generated/protocol-serial.yaml) | handshake, compatible-minor accept, unsupported-capability intersection, unsupported-major drop, CRC-invalid drop, malformed-COBS drop, truncated-frame drop, recovery with the next valid frame, sequence duplicate/gap/wraparound classes |
| [`generated/state-cycle-serial.yaml`](generated/state-cycle-serial.yaml) | `SetState(idle)` → `StateReport(idle)`, `SetState(happy)` → `StateReport(happy)`, structural sendable guard |

Generic SPI display probe (hand-written; real SPI traffic):

| Scenario | Asserts |
|---|---|
| [`generated/production-runtime.yaml`](generated/production-runtime.yaml) | the **production** loop: device-owned `booting` → `offline`, the first full frame, change-driven refresh, health cadence, `Hello`→`HelloAck`, `SetState`→`StateReport` for idle and happy, a malformed frame dropped and reported as a SAFE `Diagnostic` (category+code only), recovery on the next valid frame, and `ALL PASS production-runtime` only once all ten hold |
| [`spi-display-probe.yaml`](scenarios/spi-display-probe.yaml) | SPI peripheral + GPIO bring-up, panel reset sequenced, command/data phases distinguishable (D/C), CS-framed transactions, solid red/green/blue and checkerboard RGB565 frames, six 240×40 tiles of 9,600 pixels in top-to-bottom order, an **exact** per-frame byte volume (115,248 data + 18 command bytes), no retransmission for an unchanged frame, retransmission on a state change |

### VCD capture requires a logic analyzer part

`--vcd-file` alone produces **nothing**. Verified from an actual run: the CLI reported
`Error exporting VCD: Error 6: No logic analyzer in diagram` and wrote no file. `diagram-spi.json`
therefore includes a `wokwi-logic-analyzer` with `channelNames: "SCK,MOSI,CS,DC,RST"` on `D0`–`D4` plus
`GND`; `triggerMode` defaults to `off`, which records from the start, so no trigger wiring is needed.

Two things a real capture taught us, both now encoded in the checker and its tests:

* **Every line reads `1` at time 0.** The pins float high until the firmware configures them ~164 ms into
  boot, so the first sample is not bus activity. Measuring from time 0 made "data follows command" fail on
  a perfectly good bus. Every activity measurement is now taken **after the panel reset is released**.
* **The capture is a truncated window.** `bufferSize` is 500,000 samples (≈6.7 MB), while a full run clocks
  ~691 KB of pixel data. The checker's thresholds are deliberately below a full frame's worth for that
  reason — the VCD proves the bus behaves, and the firmware's own counters prove the exact volume.

`wokwi-cli lint` warns `Unknown attribute "channelNames"`; its attribute list is stale, and the simulator
honours it — the produced VCD declares `SCK`/`MOSI`/`CS`/`DC`/`RST`, not `D0`–`D4`.

That scenario also writes `target/wokwi-vcd/spi-display-probe.vcd`, which
[`tools/wokwi-vcd`](../../tools/wokwi-vcd) then parses: clock activity, CS/D/C transitions, a reset pulse,
data following a command phase, a minimum clocked-bit volume, and monotonic stage ordering. A capture that
cannot be parsed — or whose signals cannot be identified — **fails**; it is never accepted for existing.
Run `cargo run -p kivori-wokwi-vcd -- --list-signals <file.vcd>` to see the real signal names and adapt
`Role::candidates` from evidence.

### Marker order is part of the contract

`wait-serial` scans **forward only**, so a scenario must await markers in the order the firmware genuinely
emits them. The production-runtime scenario's first draft awaited `health-report` after
`unchanged-frame-no-reflush`; the runtime emits health on tick 1 and the first quiet frame on tick 2, so the
run hung to timeout — the same defect that once broke `state-cycle-serial`. The order now matches real
behaviour and is pinned by a host test (`emission_order_is_stable`), plus marker/firmware coupling tests in
`tools/wokwi-vectors/tests/scenario_files.rs`.

Timeouts are per-scenario wall-clock budgets, because Wokwi runs slower than real time and the production
runtime re-hashes six tiles every simulated 33 ms. Budgets never change what a scenario asserts.

A scenario fails when a `wait-serial` line never arrives (panic, hang, decode failure, missing handshake
reply, missing `Pong`, render-loop stall) or when `--fail-text` matches `KIVORI-SIM FAIL` / `panicked`.

## What this gate does **not** prove

Simulation is **not** evidence for any of the following. Each remains a physical-hardware task:

- real USB VID/PID enumeration (`0x303A:0x1001`) — T115
- Tauri opening a real serial device / desktop↔device end-to-end — T115, T117
- electrical correctness, signal integrity, pull-ups, level shifting
- **the identity of the physical panel controller** (measured on the real board as an ST7789, validation rows 1.9, 1.24, 1.25; simulation says nothing about it) — T118
- real display offsets, colour order, orientation, or any panel init sequence — T118
- the Kivori board's real SPI/CS/D/C/RST pin map — the `wokwi-spi` pins are a *simulation-only* profile
- anything analog: a VCD is a digital event list, so no signal integrity, timing margin, or level checks
- physical SPI integrity and timing — T119
- sustainable physical frame rate over SPI — T119
- physical unplug/reconnect reliability — T116, T117
- power consumption or thermal behaviour
- esp-hal `unstable` API behaviour on real silicon — T122

## Display strategy (staged)

**Stage 1 (implemented).** No display part in [`diagram.json`](diagram.json). `TileProbe` proves the
canonical renderer produces the right RGB565 tile geometry and that unchanged frames flush nothing —
without asserting anything about a controller.

**Stage 2 (implemented — T131).** [`diagram-spi.json`](diagram-spi.json) adds Wokwi's built-in
`wokwi-ili9341` and the `wokwi-spi` firmware drives it through the real T072 adapter
([`display.rs`](../../firmware/esp32-c3/src/display.rs)), so genuine SPI traffic exists to observe. Three
scopes, and only the first two are claimed:

| Scope | Claimed? | Content |
|---|---|---|
| **A — generic SPI transactions** | ✅ | peripheral init, reset sequencing, command/data phases, CS framing, transfer boundaries |
| **B — generic RGB565 tile stream** | ✅ | six 240×40 tiles, 9,600 pixels each, deterministic byte volume and order, tile Y offsets, change-driven refresh |
| **C — controller-specific behaviour** | ❌ **not claimed** | any ST7789/GC9A01/ILI9341 init sequence, panel offsets, orientation, colour order, backlight |

`wokwi-ili9341` is used **only** as a generic SPI/RGB565 sink. It does **not** validate an ST7789 (or
GC9A01) initialisation sequence — the controllers differ in init, offsets, and colour order — and a green
probe run is therefore not evidence that any real panel will light up. The adapter itself is generic over
`mipidsi`'s `Model`, so no controller is hard-coded anywhere in the firmware.

The pin numbers in `diagram-spi.json` (`SCK=4, MOSI=5, CS=6, D/C=7, RST=10`) are a **simulation-only**
profile (`WokwiSpiPins`). They were chosen from the board part's valid pins as reported by
`wokwi-cli lint` — `0–10, 18, 19, RST, RX, TX` — excluding `18`/`19` (USB Serial/JTAG on this SoC) and
`2`/`8`/`9` (ESP32-C3 strapping pins). They are **not** the Kivori hardware pin map (SCK 6, MOSI 7, D/C 2, RST 3, backlight 8, see
[`profile.rs`](../../firmware/esp32-c3/src/profile.rs)).

**Custom ST7789 chip: deliberately not created.** The physical controller is confirmed as an ST7789
(validation rows 1.9, 1.24, 1.25), but no chip model is needed yet. If one is, implement only the command subset Kivori uses — `SWRESET`, `SLPOUT`, `COLMOD`, `MADCTL`, `CASET`,
`RASET`, `RAMWR`, `DISPON` — with the Wokwi Custom Chips SPI/framebuffer APIs, and treat that chip as a
development tool, never a production dependency.

## Relationship to the other gates

```
host tests (primary)        cargo test --workspace, firmware --features host-sim, golden frames
        │
        ▼
Wokwi simulation (this)     embedded runtime + protocol/lifecycle/render on a simulated C3
        │
        ▼
physical hardware (final)   docs/validation.md — still required, still unchecked
```

Simulation may fail a change that host tests pass (e.g. a real linker/runtime problem), which is exactly
its value. It may also pass a change that a real board rejects — which is why it is never the last gate.
